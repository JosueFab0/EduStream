Cómo estudiar este manual

Este manual acompaña la defensa del código de EduStream. Permite localizar un archivo, leer su código con números de línea y entender qué hace cada instrucción o bloque corto. La explicación conecta el funcionamiento del sistema con ejemplos que se pueden demostrar al profesor.

Primero lea el panorama y los recorridos completos. Después estudie los archivos en el orden sugerido. Para una pregunta concreta, use el índice de la izquierda o la búsqueda del navegador con Ctrl+F. El buscador del manual filtra capítulos por nombre o contenido. El botón Mostrar todo restaura los capítulos. El botón Imprimir prepara la lectura completa para papel o para guardar como PDF desde el navegador.

Los números L1, L2 y siguientes corresponden a las líneas físicas de la copia local revisada el 23 de noviembre de 2026. Un bloque puede explicar varias líneas de una misma llamada. Las líneas en blanco y las llaves de cierre se conservan en el código completo. Su significado general se explica en el capítulo de sintaxis. CSS está escrito originalmente en una línea y se desglosa por regla y propiedad para que pueda estudiarse.

El manual cubre el código de la aplicación, los dos archivos de prueba, SQL, JSP, CSS, XML, Maven y los accesos locales de Windows. Las bibliotecas de Tomcat, MySQL, JUnit y sus binarios se describen por su función como dependencias. Los archivos privados de conexión se explican por su mecanismo, sin reproducir sus credenciales.

Una explicación oral útil tiene tres partes. Identifique el dato que entra, señale la validación o transformación y diga qué se devuelve o guarda. Por ejemplo, CursoService.guardar recibe el nombre del formulario, valida longitud y permiso, y llama al DAO para guardar el curso con el profesor de la sesión.

Qué ejecuta cada componente

EduStream es una aplicación web Java para gestionar cursos e inscripciones. El profesor administra sus cursos y consulta estudiantes inscritos. El estudiante consulta el catálogo, se inscribe y cancela sus propias inscripciones. Las cuentas iniciales se cargan mediante SQL.

Sintaxis Java que se repite

Clase y objeto
Una clase define datos y comportamientos. new Curso(...) crea un objeto concreto con datos para un curso. La variable guarda la referencia al objeto.
public private protected
public permite acceso desde otras clases. private restringe al interior de la clase. protected permite el uso previsto desde subclases y el mismo paquete. Los constructores de Usuario son protected y las propiedades son private.
static y final
static asocia el miembro a la clase. final impide reasignar una variable o extender una clase, según su ubicación. Un campo final que referencia un objeto no vuelve automáticamente inmutable todo ese objeto. Los modelos de este proyecto combinan campos final con ausencia de setters.
abstract extends implements
abstract permite declarar un tipo incompleto que necesita especializaciones. extends establece herencia de clase. implements obliga a cumplir una interfaz. Profesor extends Usuario y CursoService implements ICursoOperaciones muestran ambos casos.
Constructor this y super
El constructor tiene el nombre de la clase y se invoca con new. this.id señala el atributo del objeto actual. super(...) llama al constructor padre para inicializar los datos comunes.
String int Integer boolean void
String contiene texto y es inmutable. int contiene un entero de 32 bits. Integer es su envoltorio y admite null, usado al decidir si filtrar por profesor. boolean expresa true o false. void indica que el método no devuelve un valor.
null y cadena vacía
null significa ausencia de objeto. "" es una cadena existente sin caracteres. trim elimina espacios extremos. isEmpty prueba longitud cero. Un nombre " " necesita trim antes de comprobar si está vacío.
Igualdad
== compara valores primitivos o referencias de objetos. Para contenido de String se utiliza equals. La expresión "guardar".equals(accion) admite que accion sea null sin provocar NullPointerException.
Condiciones y cortocircuito
! niega, && exige dos condiciones y || acepta cualquiera de ellas. En u == null || !u.puedeGestionarCursos(), Java no evalúa la segunda parte cuando la primera ya es verdadera. Ese orden evita acceder a un objeto nulo.
Operador ternario
condicion ? valorSiVerdadera : valorSiFalsa selecciona un valor. CursoService usa u.puedeGestionarCursos() ? u.getId() : null al elegir el listado.
List<Curso> y ArrayList<>
Los genéricos indican el tipo de elementos. List es el contrato y ArrayList la implementación que crece al agregar elementos. La lista de un DAO es temporal y se llena a partir de MySQL.
return y llaves
return finaliza el método y puede devolver su resultado. Las llaves delimitan clase, método, condición o bloque. Una llave de cierre termina el bloque abierto correspondiente y no ejecuta una operación adicional.
throws throw try catch finally
throws declara que un método puede fallar con ese tipo. throw lanza una excepción concreta. try contiene el trabajo que puede fallar. catch maneja el tipo indicado y finally ejecuta una limpieza tanto ante éxito como ante error.
try con recursos
try(Connection c=...; PreparedStatement p=...) cierra automáticamente los recursos al salir. Una declaración try anidada cierra ResultSet antes de cerrar su sentencia y conexión.
Lambda en pruebas
() -> servicio.eliminar(...) es una operación que se entregará a assertThrows para ejecutarla y comprobar su excepción. No significa que JUnit la ejecute en otro hilo.
Import y package
package organiza el nombre completo de una clase. import permite escribir nombres cortos. Importar una clase no instancia objetos ni abre servicios.

Recorrido completo del inicio de sesión

  1. El navegador hace GET a la bienvenida. web.xml selecciona index.jsp, que hace forward a /login.
  2. El filtro de la petición externa fija codificación y cabeceras. Crea sesión anónima y un token si hace falta. LoginServlet.doGet entrega login.jsp.
  3. La JSP dibuja el formulario con name=email, name=password y el campo oculto csrf. El usuario envía POST.
  4. SeguridadFilter comprueba que el token recibido coincida con el de la sesión. El login no está en /app/, así que todavía no exige identidad autenticada.
  5. LoginServlet valida presencia y tamaño de parámetros. UsuarioDAO prepara SELECT por correo y Passwords.verify comprueba el derivado.
  6. Si es incorrecto, el DAO devuelve null y la misma pantalla presenta el error. Una falla de conexión produce SQLException y sigue el flujo de error técnico.
  7. Si es correcto, el DAO construye Profesor o Estudiante. LoginServlet cambia el identificador de sesión, guarda usuarioLogueado y cambia csrf.
  8. Una redirección responde al navegador con la dirección del panel. El navegador hace un GET nuevo y envía su cookie de sesión. InicioServlet consulta las cantidades y hace forward a inicio.jsp.

HttpSession contiene identidad y estado de navegación. Los datos persistentes de cursos e inscripciones se obtienen de MySQL. La cookie transporta normalmente un identificador de sesión, no una copia completa de Usuario. HttpOnly dificulta leer esa cookie desde scripts. Los atributos guardados con setAttribute quedan en el servidor.

En un forward se conserva request y sus atributos, por eso sirve para mostrar error sin perder el formulario. En sendRedirect nace una nueva petición del navegador, por eso un mensaje que debe sobrevivir se pone en sesión y flash.jsp lo retira después de mostrarlo. Un retorno temprano tras redirigir evita seguir ejecutando el resto del método.

Recorrido completo de cursos e inscripciones

Crear y editar un curso

Crear curso abre GET /app/profesor/curso sin id. El filtro exige profesor y el Servlet dibuja curso-form.jsp vacío. Guardar envía POST con accion=guardar, id=0, nombre, descripcion y csrf. CursoService comprueba rol, recorta espacios y valida longitudes. Crea un Curso cuyo idProfesor sale del usuario de sesión. CursoDAO inserta y MySQL genera la clave.

Editar agrega ?id= a la dirección del formulario. El servicio comprueba que el dueño coincida antes de mostrar sus datos. El POST mantiene el id positivo y el DAO ejecuta UPDATE con clave y dueño en el WHERE. La redirección posterior evita que una simple recarga del listado repita el envío del formulario.

Eliminar un curso

La pantalla muestra una advertencia y una casilla de confirmación del navegador. El POST incluye accion=eliminar e id. El servicio exige profesor y el DAO borra solo si la clave y el dueño coinciden. MySQL elimina en cascada las inscripciones que apuntaban a ese curso. Es una consecuencia de las claves foráneas y no un bucle que borre cada inscripción desde Java.

Inscribirse

El estudiante ve todos los cursos. Cada tarjeta envía accion=inscribir y curso con su clave. El controlador valida el id y el servicio exige estudiante y curso existente. El DAO inserta id_estudiante desde la sesión y fecha con CURRENT_DATE. Si la pareja ya existe, UNIQUE genera 1062 y se convierte en InscripcionDuplicadaException.

Consultar y cancelar inscripciones

El profesor recibe registros de sus cursos. El estudiante recibe solo sus registros. El mismo DAO selecciona una de dos condiciones SQL según el objeto Usuario. Cancelar envía id_inscripcion y el DAO agrega id_estudiante de sesión al DELETE. Cambiar un id en el navegador no concede el permiso sobre una inscripción ajena.

Qué pasa al reiniciar

Las conexiones y listas temporales desaparecen al detener el proceso Java. Los archivos del directorio de datos de MySQL conservan tablas y filas. Al volver a iniciar, una consulta nueva reconstruye las listas. La sesión puede requerir autenticación de nuevo o conservarse según el manejo del contenedor. La prueba de persistencia de datos debe comprobar las filas y no asumir que la sesión sobrevivió.

Cómo leer las consultas y las relaciones

Usuarios guarda identidad y rol. Cursos tiene un id_profesor que referencia usuarios. Inscripciones tiene id_estudiante e id_curso que referencian a sus padres. Un profesor puede tener muchos cursos y un estudiante puede tener muchas inscripciones. Cada curso también puede tener muchas inscripciones. Esta tabla intermedia resuelve la relación de muchos estudiantes con muchos cursos.

Una clave primaria identifica una fila. Una clave foránea exige que exista la clave del padre. UNIQUE(id_estudiante,id_curso) restringe la pareja completa. Ni la clave foránea id_profesor ni id_estudiante comprueban la etiqueta rol del usuario, por eso los servicios aplican ese control. Un administrador que modifique las tablas directamente puede producir asignaciones de roles inconsistentes aunque las claves existan.

SELECT lee. INSERT crea una fila. UPDATE modifica y DELETE elimina. WHERE restringe qué filas intervienen. JOIN reúne filas relacionadas. En SELECT c.*,u.nombre profesor, c.* toma todas las columnas del curso y profesor es un alias para el nombre del usuario. El DAO usa ese alias al leer r.getString("profesor"). ORDER BY id DESC presenta ids mayores primero.

PreparedStatement recibe una estructura SQL conocida y valores por posición, empezando en 1. La instrucción WHERE email=? y setString(1,email) mantienen el correo como dato. Los ? no sirven para elegir dinámicamente nombres de tablas. Las concatenaciones de listar solo eligen entre fragmentos constantes del programa.

executeQuery corresponde a consultas que devuelven filas. executeUpdate corresponde a modificaciones y devuelve un recuento. RETURN_GENERATED_KEYS solicita la clave de un INSERT. ResultSet es un cursor que empieza antes de la primera fila. r.next() avanza y devuelve false al agotarse. Leer columnas antes de avanzar es un error.

El código abre conexiones con el comportamiento normal de autocommit y no define transacciones manuales con setAutoCommit(false), commit o rollback. Cada sentencia de modificación se confirma individualmente. Una eliminación en cascada se aplica como parte de la integridad de esa sentencia en InnoDB. Si se añadiera una operación de varios cambios que deban confirmarse juntos, se tendría que diseñar una transacción que comparta conexión.

Cómo se generan las pantallas

HTML define títulos, enlaces, formularios y tablas. CSS define su presentación. JSP permite que el servidor genere ese HTML con los datos que recibe. Tomcat traduce las JSP a Servlets y las compila cuando corresponde. El navegador recibe el resultado generado.

Las expresiones ${curso.nombre} llaman al getter getNombre del objeto Curso. ${sessionScope.usuarioLogueado.rol} identifica un atributo de sesión y obtiene su rol. Una expresión sin prefijo puede buscar atributos entre los alcances página, petición, sesión y aplicación. Los controladores del proyecto usan request para listas y errores y session para identidad, token y mensajes de redirección.

c:forEach recorre listas, c:if evalúa una condición y c:choose agrupa alternativas c:when y c:otherwise. c:out imprime con escape para mostrar texto como <script> de forma literal. El lenguaje de expresiones por sí solo no realiza ese escape de salida, por eso los textos escritos por usuarios se imprimen con c:out.

jsp:include inserta la salida de otro recurso en la misma respuesta. nav.jsp y flash.jsp evitan repetir esa lógica. jsp:forward entrega la generación de respuesta a otro recurso. Estas acciones JSP se ejecutan en el servidor. El código de las vistas del proyecto no contiene un framework de interfaz JavaScript.

id identifica un elemento en HTML y permite asociarlo a label. name identifica el parámetro enviado al servidor. action determina el destino del formulario y method determina GET o POST. Un botón dentro de form envía por defecto el formulario. type=hidden oculta el control visualmente, pero su dato sigue siendo inspeccionable y modificable desde el cliente.

required, maxlength y type=email mejoran la entrada del navegador. Las reglas críticas deben volver a verificarse en Java. Los permisos se comprueban por filtro, servicio y condición SQL. Ocultar Crear curso al estudiante no sería suficiente si el servidor aceptara su POST.

Controles y límites de la versión actual

La aplicación comprueba identidad con el derivado de contraseña y usa sesiones para solicitudes posteriores. La autorización se aplica por rol y por propietario. Los parámetros SQL evitan tratar entradas del formulario como instrucciones. c:out escapa textos hacia HTML. El token csrf vincula el envío de formularios con la sesión que los abrió. Las cabeceras reducen determinadas formas de contenido y marcos no esperados.

Estos controles resuelven riesgos distintos. Un usuario autenticado todavía necesita permiso sobre cada curso. Un token correcto todavía puede acompañar un id ajeno que debe rechazarse. Una consulta preparada no protege por sí misma la salida HTML. La protección de la contraseña almacenada no cifra el transporte HTTP entre navegador y servidor.

La versión usa HTTP local. No configura HTTPS, limitación de intentos de login, recuperación de contraseña, alta pública de cuentas, auditoría persistente ni gestión de usuarios desde pantalla. Los roles activos están en la identidad de sesión. Si un administrador cambia un rol directamente en MySQL, la sesión existente no se refresca automáticamente con ese cambio.

La comprobación de existencia del curso y el INSERT de inscripción son sentencias separadas y pueden competir con una eliminación. La clave foránea mantiene la integridad y el controlador contempla 1452. La unicidad de inscripciones también se decide en MySQL, de modo que dos envíos simultáneos no deben crear dos filas con la misma pareja.

El checkbox de eliminación pertenece a la confirmación visual del navegador. No se envía como una condición verificada por Java. Los listados no están paginados y el panel cuenta colecciones cargadas completas. La conexión se abre por operación y no se implementa un pool. Son características concretas que se pueden explicar al evaluar límites y futuras mejoras.

Preguntas y respuestas para la defensa

Estas preguntas se responden a partir del código examinado. Las respuestas distinguen comportamiento implementado, decisiones de diseño y límites que deben explicarse con precisión.

Entorno

1. ¿Qué tipo de aplicación es EduStream?

Es una aplicación web Java. Se utiliza desde un navegador y el código de servidor se ejecuta en Tomcat. Usa MySQL para guardar usuarios, cursos e inscripciones. La interfaz actual está hecha con JSP, HTML y CSS. Una versión de escritorio requeriría construir su interfaz y adaptar la entrada y salida de los controladores HTTP.

Dónde comprobarlo · pom.xml, web.xml

2. ¿Qué diferencia hay entre NetBeans, Java, Maven y Tomcat?

NetBeans es el entorno para trabajar el proyecto. Java es el lenguaje y su plataforma de ejecución. Maven compila, prueba y empaqueta mediante pom.xml. Tomcat ejecuta la aplicación web ya compilada y atiende las solicitudes HTTP.

Dónde comprobarlo · pom.xml

3. ¿Cuál framework utilizaron?

El código utiliza Servlets, JSP, JSTL y JDBC directamente. Se organiza con los patrones modelo, vista y controlador y DAO. Tomcat es el contenedor web, NetBeans el IDE y JUnit la biblioteca de pruebas. Las dependencias exactas se pueden enseñar en pom.xml.

Dónde comprobarlo · pom.xml

4. ¿Con qué hicieron el diseño?

Con HTML y CSS propios. Las JSP generan el HTML con los datos enviados por Java. style.css define colores, espacios, tarjetas, tablas y ajustes para pantallas pequeñas. No hay una dependencia de Bootstrap en el proyecto.

Dónde comprobarlo · style.css, cursos.jsp

5. ¿Por qué se eligió Tomcat 9?

Los Servlets importan javax.servlet y el descriptor web es versión 4.0. Tomcat 9 proporciona esos contratos. Cambiar a una familia que utiliza jakarta.servlet implica revisar compatibilidad y migrar imports y dependencias.

Dónde comprobarlo · web.xml, LoginServlet.java

6. ¿Qué hace un WAR?

Es el paquete de la aplicación web. Reúne clases compiladas, JSP, CSS, descriptor web y dependencias que deben desplegarse. Maven lo crea como target/edustream.war. El servidor aporta la API Servlet declarada provided.

Dónde comprobarlo · pom.xml

7. ¿Por qué localhost a veces tiene /edustream y a veces no?

Depende del contexto de despliegue. NetBeans llegó a desplegar la aplicación en la raíz. Copiar edustream.war a webapps permite desplegarla como /edustream. Las páginas y redirecciones usan contextPath para construir las rutas correspondientes.

Dónde comprobarlo · context.xml, Web.java

8. ¿El puerto 8080 es la base de datos?

8080 es el puerto HTTP de Tomcat en esta instalación. MySQL utiliza 3306. El navegador se comunica con Tomcat y Java se comunica con MySQL usando JDBC. El navegador no envía consultas directamente al puerto de MySQL.

Dónde comprobarlo · Conexion.java, iniciar-local.ps1

9. ¿Se trabajó con GitHub?

El proyecto se preparó localmente en la computadora y se empaquetó en ZIP. Un archivo .gitignore solo define exclusiones para un eventual uso de Git. Su presencia no indica que exista un repositorio remoto o un historial de commits.

Dónde comprobarlo · .gitignore

El modelo de datos está en model, la persistencia en dao y las reglas en service. Las vistas están en WEB-INF/views. Los controladores están en web y extienden HttpServlet. El filtro es una pieza transversal anterior a esos controladores.

El servicio expresa permisos y validaciones de negocio. El DAO conoce SQL, conexiones y mapeo de filas. Así la pantalla no consulta MySQL y el DAO no tiene que interpretar formularios HTTP. Una regla de rol se puede probar sin llegar a abrir conexión.

HTTP y sesiones

37. ¿Cuál es la diferencia entre GET y POST en el proyecto?

GET abre panel, formularios y listados. POST autentica o modifica mediante guardar, eliminar, inscribir, cancelar y salir. El filtro exige csrf en los POST. Usar POST no cifra automáticamente el contenido.

38. ¿Para qué sirve HttpSession?

Relaciona peticiones del mismo navegador con atributos del servidor. Se guarda usuarioLogueado, csrf y mensajes temporales. La cookie permite que Tomcat encuentre esa sesión entre solicitudes HTTP que por sí solas son independientes.

39. ¿Qué diferencia hay entre request y session?

request dura durante una petición y sus despachos internos. Se usa para listas y errores de formulario. session conserva información entre peticiones del mismo usuario y se usa para identidad, token y mensajes tras una redirección.

40. ¿Cuándo usan forward y cuándo redirect?

Se guardan derivadas con PBKDF2. La verificación calcula un derivado usando la misma salt y compara los bytes. No se implementa una operación para descifrar o recuperar la contraseña original. Base64 solo representa los bytes como texto.

Es un valor aleatorio que acompaña a la contraseña al derivar. hash genera 16 bytes y los guarda codificados como parte del texto pbkdf2. No necesita ser secreto. Las cuentas iniciales usan una salt fija compartida como datos de demostración.

Errores

60. ¿Qué diferencia hay entre error de negocio y técnico?

Nombre vacío, curso ajeno o inscripción repetida son rechazos esperados que se comunican con NegocioException. Un fallo de conexión o consulta es SQLException y se propaga como ServletException hacia la página genérica del contenedor.

Dónde comprobarlo · NegocioException.java, CursoServlet.java, error.jsp

61. ¿Qué significan 400 403 404 405 y 500?

400 es una solicitud que la aplicación no acepta. 403 es permiso o token rechazado. 404 es una ruta inexistente. 405 es un método no admitido para el destino. 500 indica un fallo interno. web.xml los dirige a error.jsp.

Dónde comprobarlo · web.xml, error.jsp

62. ¿Por qué se usan los números 1062 y 1452?

Son códigos de error MySQL. 1062 se traduce a inscripción duplicada y 1452 se interpreta como relación que dejó de estar disponible al insertar. Las demás SQLException siguen como errores técnicos. Estos números son específicos del motor utilizado.
